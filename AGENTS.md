# WinDeploy: инструкции агентам

- Начните с `git status`, текущей ветки и `git log -20 --oneline`; прочитайте AGENTS.md, HANDOFF.md, TASKS.md, README.md, docs/BETA_READINESS.md и относящуюся к задаче документацию/исходники. Git и работающий код важнее старых галочек.
- **Приоритет — безопасная публичная beta v0.1.0-beta.1, а не завершение roadmap.** Windows 11 x64 — основная и проверенная платформа. Windows 10 x64/совместимые LTSC можно поддерживать только без неподтверждённых заявлений; beta scope сейчас — Windows 11 x64.
- **Одна итерация — 2–4 задачи.** Сначала BETA BLOCKER, затем BETA REQUIRED. Не начинать новые крупные модули; не переносить security-проблемы в POST-BETA ради скорости. У каждой блокирующей задачи должно быть конкретное доказательство: код, тест, воспроизводимая ошибка или риск.
- Windows 7/Legacy — **FROZEN**. Не добавлять Legacy features/fixes/tests, не включать Legacy в Modern CI/release и не начинать Win7 VM-матрицу без отдельного решения владельца. Не удалять существующие Legacy-код/тесты/документацию.
- **VM acceptance больше не является обязательным общим критерием beta.** Конкретные изменяющие сценарии без VM/разрешения обозначать как экспериментальные или непроверенные; не выдумывать E2E-результаты. Реальные установки, SMB, драйверы, принтеры, политики и reboot проверять на одноразовой VM либо с отдельного разрешения владельца.
- Root остаётся Go 1.20; версию автоматически не повышать. Modern-specific зависимости изолированы в `desktop/modern`. Версия проекта — единый `VERSION`; UI/EXE/release не должны иметь второй hard-coded номер.
- Бизнес-логика вне UI, небольшие интерфейсы/DI, context cancellation, Windows API в адаптерах. Проверяйте реальный результат, пользователя/SID и user/machine scope; preview не заменяет runtime safety gate. Не создавать фиктивный Success.
- Можно отключать опасный сценарий на уровне backend с явным Known Issue; disabled-кнопка в UI без backend-запрета не считается отключением. Не ослаблять SID/session/ACL/installer trust gates и не обходить их «для удобства».
- После изменения: diff, gofmt, релевантные test/vet/build; для frontend — strict typecheck, существующие UI tests/build. Отличайте сборку EXE от реального desktop/bridge smoke. Недоступные проверки указывать явно.
- Для тестов используйте `scripts/test-core.ps1`; не отключайте failing tests и не маскируйте flake бесконечными retry. Temp/ACL/OneDrive-ограничения документируйте, а не выдавайте за production-результат. Не меняйте глобальные настройки Windows ради тестов.
- После логического изменения обновите статус и сделайте осмысленный отдельный коммит (`feat`, `fix`, `test`, `docs`, `chore`). Добавляйте только нужные файлы. Не меняйте глобальную Git identity, не перезаписывайте чужую работу, не используйте force push/reset hard.
- Не коммитить secrets, credentials, EXE, ZIP, caches, runtime logs, inventory с персональными данными или скриншоты с hostname/IP/именами. Sessions требуют trusted local storage и Windows ACL; 0600 не является гарантией ACL.
- **Публичный Release/репозиторий не создавать без явного подтверждения владельца.** До этого: LICENSE выбран, owner/repo URL зафиксирован, Git-история проверена, CI PASS, draft Release проверен. Не объявлять релиз опубликованным без GitHub-подтверждения.
- В конце итерации обновить TASKS.md, docs/BETA_READINESS.md и все разделы HANDOFF.md: этап, готовность, закрытые/открытые blockers, коммиты, реальные тесты, архитектура, Git, следующие 2–4 задачи, точные команды, ограничения безопасности и условия разрешения публикации. После документационного коммита проверить git status и остановиться.
- В отчёте указать ветку, хеши, реальные результаты и ближайшую задачу. Не называть проверку Windows 11 подтверждением Windows 10/LTSC или Win7.
