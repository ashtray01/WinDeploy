## Что уже реализовано
Документация назначения, roadmap, правила агентов и исключения Git.
Go-модуль `windeploy` с `go 1.20`, без зависимостей; `core/doc.go`, `docs/architecture.md`.
`core/engine/task.go`: Task, OSRequirements, девять статусов из ТЗ, Valid, структурная Validate, TaskResult. Модели поддерживают JSON, timeout — наносекунды.
Unit-тесты статусов, некорректных описаний задач и JSON round-trip.
`core/engine/plan.go`: OrderTasks проверяет Task.Validate, дубли ID, неизвестные ссылки и циклы; возвращает стабильный топологический порядок без изменения входа. При ошибке нет частичного результата.

`executor.go`: Run и Adapter с Precheck/Execute/Verify; валидация всего Pending-плана до запуска, последовательный обход DAG, результаты/время, пропуск заблокированных задач, отмена и timeout. Исходный Task не обновляется. Execute может вернуть флаг перезагрузки, успех подтверждается Verify.
`executor_test.go`: fake-адаптеры, порядок фаз, ошибки каждой фазы, короткое завершение Precheck, блокировка зависимостей и продолжение независимых задач, отказ невалидному/не-Pending плану, отмена до начала/во всех фазах, timeout во всех фазах и истёкший родительский deadline.

## Что сейчас не работает
Нет GUI, реальных системных адаптеров, dry-run, retries, параллельности, сохранения состояния, автоматического маскирования секретов. Run отбрасывает сырой текст ошибок адаптера и сохраняет только этап: подробная безопасная диагностика ещё отсутствует. Проверка ОС — обязанность будущего Precheck. Go 1.20 и целевая матрица Windows (включая Windows 7 SP1 x86/x64) не проверялись. Нет оснований заявлять подтверждённую совместимость.

## Архитектурные решения
Целевое требование ядра — Go 1.20. Использованы только базовые API стандартной библиотеки; проверка старым toolchain остаётся обязательной.
Task — сериализуемое описание. Precheck/Execute/Verify — отдельный Adapter с context; не хранить функции в Task. Нулевой статус недопустим, Pending задаётся явно. Parameters — map[string]string без секретов.
UI и Windows-адаптеры отделены от бизнес-логики. Непонадобившиеся каталоги и внешние зависимости не создавались.
OrderTasks использует алгоритм Кана с выбором наименьшего исходного индекса среди готовых задач. Сложность O(V² + E); для текущих небольших планов дополнительная структура приоритетов не вводилась. Результат — новый срез поверхностных копий: вложенные maps/slices разделяются, это явно указано в API. Диагностика цикла перечисляет неразрешённые задачи, в том числе заблокированные циклом.
Run принимает только Pending, не переисполняет готовые задачи. Adapter не должен изменять вложенные данные Task. Precheck разрешает Pending/AlreadyInstalled/NotApplicable/Skipped, прочие исходы становятся Failed. Только Success/AlreadyInstalled удовлетворяют зависимостям. Success с RebootRequired=true разрешает зависимости, так как Verify обязан подтвердить готовность.
Timeout общий для трёх фаз; локальное истечение — Failed, отмена/deadline родителя — Cancelled. Ошибки отдельных задач нужно читать из результатов; error Run используется для входных ошибок и ctx.Err(). Run синхронно ждёт завершения адаптера. Реестр адаптеров, системные команды, detailed errors и lifecycle events не добавлялись.
